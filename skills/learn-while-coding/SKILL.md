# コーディングしながら学ぶ

このSkillは、ユーザーが実際に取り組んでいるプロジェクトのコードを対象に、
「AIが出した機能を自分のスキルとして理解する」ことを支援する。
生成したサンプルアプリではなく、**今まさに書いている実プロジェクトの実コード**を使うこと。

`output-input-learning` というMCPサーバーが提供する2つのツールを使う:
- `build_stack_graph_widget` — 技術スタックの関係図(SVG)を組み立てる
- `build_code_blank_widget` — 実コードから穴埋め演習ウィジェット(HTML)を組み立てる

どちらのツールも `widgetCode` という文字列を返すので、それを **必ず `visualize` (show_widget) ツールに渡してそのまま描画すること**。
widget自身には説明文を含めない設計になっている。説明は必ずこのSkillの手順に従い、通常のチャット応答テキストとして書くこと。

## 絶対に守る順序: 基礎の説明 → 可視化・演習

ユーザーからのフィードバックで最も重要な指摘は「いきなり穴埋めさせても分からない」というものだった。
そのため、**可視化や穴埋め演習を出す前に、必ず平易な言葉で基礎を説明する**。説明を飛ばして
いきなりウィジェットだけを出すことは禁止。

### 1. 技術スタックを選んだとき

1. まず通常の応答テキストで、選んだ技術それぞれについて「何をするものか」「なぜこの企画に必要か」を
   2〜3文程度で平易に説明する(専門用語を使う場合は一言で言い換える)。
2. 技術ノード(3〜8個)とエッジを組み立てる。エッジの `dataFlow` には、**その2つの技術の間で実際に
   何のデータがどんな形式でやり取りされるか**を5語程度で書く(例: 「JSON形式のフォーム入力」「SQLクエリ結果」
   「認証済みセッションCookie」)。ここが今回追加で必須になった要件で、ノード一覧を眺めるだけでなく
   「AとBの間でデータがどう受け渡されるか」が図から読み取れるようにする。
3. `build_stack_graph_widget` を呼び、返ってきた `widgetCode` を `visualize` に渡して描画する。
4. 図を出した直後に、図だけでは伝わらない補足(例えば代表的なエッジについて1文程度)があれば
   通常テキストで補う。図の中に長い説明を書き込まない。

### 2. 意味のあるコードを書き終えたとき

1. コードを書く/生成する(通常通り)。
2. 穴埋め演習を出す**前に**、そのコードで何が重要かを2〜3文で平易に説明する
   (例:「ここでは`useState`でカウントの状態を管理しています。ボタンを押すたびに
   `setCount`が呼ばれて画面が再描画されます」)。この説明を省略しない。
3. 学習に適した意味のある単位(状態管理・イベントハンドラ・API呼び出し・重要なロジックなど)を
   2〜6個選び、`blanks` としてまとめる(各blankは元コードからの厳密な抜粋・役割ラベル・
   もっともらしい誤答1〜3個を持つ)。1トークンや1文字のような細かすぎる空欄にしない。
4. `build_code_blank_widget` を呼び、返ってきた `widgetCode` を `visualize` に渡して描画する。
5. コード中の空欄が、直前1で選んだ技術スタックのどれかと関係している場合は、
   説明テキストの中でその対応関係にも触れる(例:「この空欄はZustandによる状態管理の部分です」)。

## 注意点

- 大袈裟に使いすぎない。些細な1行の変更のたびに図や演習を出すと煩雑になる。
  技術選定の節目、または学習価値の高いコードを書いた節目でのみ使う。
- ウィジェットは`visualize`のデザインシステム(CSS変数、flatなスタイル、絵文字なし、
  タイトル文をウィジェット内に書かない等)に従う。widgetCode自体は既にこれに沿って
  組み立てられているので、そのまま渡せばよい。
- `build_code_blank_widget` の `blanks[].text` は実コードからの一字一句そのままの抜粋であること。
  要約や言い換えをすると空欄の位置特定に失敗する。
